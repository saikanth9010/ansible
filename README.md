# Proxmox LXC Automated Provisioning Workflow

## 📌 Project Overview
This project automates the entire lifecycle of a Linux Container (LXC) on Proxmox. It moves beyond simple "creation" by handling networking, security, and OS-level provisioning in one seamless execution.



## 🏗️ The Architecture (The "Two-Play" System)
Ansible operates on two different "planes" in this project. Understanding this is critical for troubleshooting:

### 1. The Management Plane (Play 1)
* **Target:** `localhost` (Your MacBook).
* **Communication:** HTTPS/REST API (Port 8006).
* **Goal:** Tell Proxmox what to build.
* **Logic:** We use API Tokens because they are more secure and easier to revoke than root passwords. We must explicitly call `state: started` because creating a container does not automatically boot it in the Proxmox API.

### 2. The Configuration Plane (Play 2)
* **Target:** `10.0.0.156` (The New Container).
* **Communication:** SSH (Port 22).
* **Goal:** Configure the internal OS.
* **Logic:** This play "waits" for the container to finish booting. It uses a temporary inventory (`add_host`) because the container didn't exist when the playbook started.

## 🛡️ Firewall & Security Deep Dive
Proxmox's firewall is hierarchical. Even if the OS allows SSH, the Proxmox hardware-level firewall will drop the packets unless configured.

* **Interface Level:** We pass `firewall=1` in the `netif` string. This tells Proxmox to "plug in" the firewall cable to that specific virtual network card.
* **Rule Level:** The `proxmox_firewall` module is strict. 
    * `pos: 0`: Sets the priority.
    * `dport: 22`: The destination port for SSH.
    * `type: in`: Handles inbound traffic.

## 🔑 SSH & Authentication Logic
We solved the "New Host" paradox using three layers:
1.  **Creation Key:** The `pubkey` parameter in Play 1 places your MacBook's key into `/root/.ssh/authorized_keys` at the moment of birth.
2.  **Fingerprint Bypass:** We use `ansible_ssh_extra_args` to ignore "Host Key Verification." This is necessary because every new container generates a new unique fingerprint, which would normally trigger a security warning on your Mac.
3.  **User Transition:** We move away from the `root` user immediately by creating the `sai` user. By placing a file in `/etc/sudoers.d/sai`, we ensure that the `sai` user can perform administrative tasks without being prompted for a password, which is essential for future automation.

## 🛠️ Maintenance & Troubleshooting

### Error: "No route to host"
**Cause:** Your MacBook cannot see `10.0.0.144`.
**Fix:** Check your VPN or Wi-Fi. Ensure you can `ping 10.0.0.144`.

### Error: "Host Identification Changed"
**Cause:** You deleted a container and made a new one with the same IP (`10.0.0.156`).
**Fix:** Run `ssh-keygen -R 10.0.0.156` on your Mac.

### Variable Reference
* `vault_proxmox_token_secret`: The UUID generated by Proxmox.
* `vault_root_password`: Used for the initial root login during Play 2.
* `ostemplate`: The specific Debian `.tar.zst` file located in your Proxmox ISO/Template storage.

## 📈 Future Expansion
To add more containers, simply change the `vmid` and `ip` in the `vars` section. You can also add `apt` tasks to Play 2 to pre-install Docker, Nginx, or other tools you need for your lab.
